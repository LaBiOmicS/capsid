# Recipe reference

A **recipe** (`recipes/<name>/<version>/recipe.yaml`) describes how to package one version of one
tool. A **stack** (`stacks/<name>.yaml`) combines several recipes into one image. This page lists
every field of both formats.

## File layout

```
recipes/
└── samtools/                 # <name>: lowercase, becomes the image name
    └── 1.25/                 # <version>: becomes the image tag
        ├── recipe.yaml
        └── pixi.lock         # or requirements.lock; generated by `capsid lock`
stacks/
├── variant-calling-stack.yaml
└── variant-calling-stack.pixi.lock
```

The directory names must equal the recipe's `name` and `version` (linter rules `E003`, `E004`).
Each version lives in its own directory, so old versions stay buildable when new ones are added.

## Top-level fields

| Field | Type | Required | Description |
| :--- | :--- | :---: | :--- |
| `name` | string | yes | Tool name. Lowercase letters, digits, `.`, `_`, `-`, starting with a letter or digit (`^[a-z0-9][a-z0-9._-]*$`). Used as the image name. |
| `version` | string | yes | Tool version. Letters, digits, `.`, `_`, `+`, `-`, at most 128 characters. Used as the image tag. Quote versions that YAML would read as numbers (`'1.25'`, not `1.25`). |
| `description` | string | | One-line summary. Stored in the `org.opencontainers.image.description` label. |
| `homepage` | URL | | Project homepage or repository. |
| `license` | string | | [SPDX](https://spdx.org/licenses/) identifier or expression, e.g. `MIT`, `GPL-3.0-or-later`, `Apache-2.0 OR MIT`. |
| `categories` | list of strings | | Free-form tags shown in the catalog (e.g. `genomics`, `alignment`). |
| `doi` | string | | DOI of the tool or its publication. |
| `edam_topics` | list of strings | | [EDAM](https://edamontology.org) topic IDs, e.g. `topic_0080`. |
| `edam_operations` | list of strings | | EDAM operation IDs, e.g. `operation_0292`. |
| `platforms` | list | | Target architectures: `linux/amd64`, `linux/arm64`. Default: both. |
| `build` | object | yes | How to build the tool; see [`build`](#build). |
| `test` | object | yes | How to verify the image; see [`test`](#test). |
| `labels` | map string → string | | Additional OCI labels. |
| `ro_crate` | object | | Extra JSON-LD for the embedded RO-Crate; see [Metadata](#metadata-fair-ro-crate-and-labels). |

## `build`

### Build types

| `type` | Installs | Builder stage | Typical use |
| :--- | :--- | :--- | :--- |
| `pixi-conda` | Conda packages, resolved by [pixi](https://pixi.sh) | `ghcr.io/prefix-dev/pixi` | Most bioinformatics tools (Bioconda + conda-forge) |
| `uv-pypi` | A PyPI package into a virtual environment, with [uv](https://docs.astral.sh/uv/) | Official `python:<version>-slim-bookworm` | Pure-Python and wheel-based tools |
| `autotools` | A source archive with `./configure && make && make install` | `debian:bookworm-slim` | GNU-style projects |
| `make` | A source archive with a plain `Makefile` | `debian:bookworm-slim` | Projects without a configure step (e.g. `bwa`, `lz4`) |
| `cmake` | A source archive with CMake | `debian:bookworm-slim` | CMake projects |
| `rust-cargo` | A Rust crate source archive with `cargo install --locked` | `rust:<version>-slim-bookworm` | Command-line tools written in Rust |
| `binary` | Prebuilt executables, one archive per architecture | `debian:bookworm-slim` | Tools distributed as release binaries |

Every builder image is pinned by digest. The runtime image is `debian:bookworm-slim` (or the matching
`python:<version>-slim-bookworm` for `uv-pypi`), also pinned by digest. See
[Image design](image-design.md).

Prefer `pixi-conda` when the tool is on Bioconda or conda-forge: the package is already built and
tested for both architectures, and the lockfile pins the whole dependency tree.

### `pixi-conda`

```yaml
build:
  type: pixi-conda
  conda_packages: [samtools==1.25]
  channels: [conda-forge, bioconda]
```

| Field | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `conda_packages` | list of strings | — | Conda match specs. **Required.** Pin the tool exactly with `==` (`W012` otherwise). Extra packages (for example `pigz` or `python=3.12`) can be listed too. A `channel::name==version` prefix selects a channel for one package. |
| `channels` | list of strings | `[conda-forge, bioconda]` | Channels in priority order (strict priority). |

The environment is installed at `/opt/conda-env` and its `bin/` is on `PATH`. With a `pixi.lock` the
build runs `pixi install --locked`, so it fails instead of silently resolving something different.

### `uv-pypi`

```yaml
build:
  type: uv-pypi
  package: cutadapt==5.2
  python_version: '3.12'
```

| Field | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `package` | string | — | PyPI requirement. **Required.** Pin with `==` (`W012` otherwise). Extras are allowed: `multiqc[all]==1.25.1`. |
| `python_version` | string | `'3.12'` | Python of the virtual environment: `3.10`, `3.11`, `3.12` or `3.13`. Other versions need `base_image` (`E013`). |

The virtual environment is installed at `/opt/venv`. The builder and the runtime use the same
official Python image, so the interpreter the venv links to exists in both stages. With a
`requirements.lock` the build runs `uv pip install --require-hashes`, which refuses any file whose
hash differs from the lockfile.

Packages that compile C extensions may need system headers in `dependencies.build` and the
corresponding shared libraries in `dependencies.run`.

### `autotools`, `make`, `cmake`, `rust-cargo`

```yaml
build:
  type: autotools
  source: https://ftp.gnu.org/gnu/hello/hello-2.12.1.tar.gz
  sha256: 8d99142afd92576f30b0cd7cb42a8dc6809998bc5d607d88761f512e26c7db20
  configure_args: [--disable-nls]
  dependencies:
    build: [zlib1g-dev]
    run: [zlib1g]
```

| Field | Type | Applies to | Description |
| :--- | :--- | :--- | :--- |
| `source` | URL | all four | Source archive (`.tar.gz`, `.tar.bz2`, `.tar.xz`, …). **Required.** Use `https://` (`W013`). |
| `sha256` | string | all four | SHA-256 of the archive. **Required** (`E011`). The download is verified with `sha256sum -c` before it is unpacked. Quote it if it contains only digits. |
| `configure_args` | list | `autotools` | Extra `./configure` arguments. |
| `cmake_args` | list | `cmake` | Extra arguments for the CMake configure step, e.g. `-DBUILD_TESTING=OFF`. |
| `cargo_args` | list | `rust-cargo` | Extra `cargo install` arguments, e.g. `--features`, `--bin`. |
| `install_prefix` | path | all four | Installation prefix. Default: `/opt/<name>`. Its `bin/` is put on `PATH`. |
| `build_commands` | list | all four | Shell commands that **replace** the default steps below. |

The archive is unpacked with its top-level directory stripped, and the default steps run from there:

| Type | Default steps |
| :--- | :--- |
| `autotools` | `autoreconf -fi` when there is no executable `configure`; then `./configure --prefix=<prefix> <configure_args>`, `make -j$(nproc)`, `make install` |
| `make` | `make -j$(nproc) PREFIX=<prefix> prefix=<prefix>`, then `make install PREFIX=<prefix> prefix=<prefix>` |
| `cmake` | `cmake -S . -B /src/build -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=<prefix> -DCMAKE_INSTALL_RPATH=<prefix>/lib <cmake_args>`, then `cmake --build` and `cmake --install` |
| `rust-cargo` | `cargo install --locked --path . --root <prefix> <cargo_args>` |

Notes:

- C/C++ builds get `LDFLAGS=-Wl,-rpath,<prefix>/lib`, so installed binaries find their own shared
  libraries without `LD_LIBRARY_PATH`.
- Binaries in `<prefix>/bin` are stripped after the build.
- The builder already has a toolchain: `build-essential` and `pkg-config` for every type, plus
  `autoconf`, `automake` and `libtool` for `autotools` and `cmake` for `cmake`. Add libraries
  (`zlib1g-dev`, `libbz2-dev`, …) to `dependencies.build` and their runtime packages
  (`zlib1g`, `libbz2-1.0`, …) to `dependencies.run`.
- `rust-cargo` uses `--locked`: the project's own `Cargo.lock` decides every dependency version.
  Crates without a `Cargo.lock` in the release archive cannot be built this way.
- Only `<prefix>` is copied to the runtime image. A Makefile that ignores `PREFIX`/`prefix` needs
  `build_commands`.

Example with `build_commands` (a Makefile without an install target):

```yaml
build:
  type: make
  source: https://github.com/lh3/bwa/archive/refs/tags/v0.7.19.tar.gz
  sha256: <sha256 of the archive>
  build_commands:
    - make -j"$(nproc)"
    - install -D -m 0755 bwa /opt/bwa/bin/bwa
  dependencies:
    build: [zlib1g-dev]
    run: [zlib1g]
```

### `binary`

```yaml
platforms: [linux/amd64, linux/arm64]
build:
  type: binary
  binary_url_amd64: https://github.com/shenwei356/seqkit/releases/download/v2.8.2/seqkit_linux_amd64.tar.gz
  sha256_amd64: a6515a64bf28ceba6922a3854d8ec898ca2ca637b4b00fc883c83076dfaf1ffa
  binary_url_arm64: https://github.com/shenwei356/seqkit/releases/download/v2.8.2/seqkit_linux_arm64.tar.gz
  sha256_arm64: 8c12816c0bf6c01cfcda329fdb5f6c1479cf2485ce9413ce36b96237524da9dc
```

| Field | Type | Description |
| :--- | :--- | :--- |
| `binary_url_amd64`, `binary_url_arm64` | URL | Release artefact for each architecture in `platforms`. **Required** per listed platform (`E012`). |
| `sha256_amd64`, `sha256_arm64` | string | SHA-256 of each artefact. **Required** (`E011`). |
| `install_prefix` | path | Default `/opt/<name>`. |
| `build_commands` | list | Replaces the default installation step (runs in the unpacked artefact). |

The build downloads the artefact for the architecture being built (`TARGETARCH`), verifies its
checksum and unpacks it by extension: `.tar.*`/`.tgz` with `tar`, `.zip` with `unzip`, a lone `.gz`
with `gunzip`; anything else is installed as the executable `<name>`. By default every executable
file found in the artefact (up to four directory levels deep) is installed into `<prefix>/bin`.
Prebuilt binaries are not stripped.

### Fields shared by all build types

| Field | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `dependencies.build` | list | `[]` | Debian packages installed in the builder stage only. |
| `dependencies.run` | list | `[]` | Debian packages installed in the runtime image. |
| `env` | map | `{}` | Environment variables set in the runtime image. |
| `apt_snapshot` | string | Capsid's pinned snapshot | `snapshot.debian.org` timestamp (`YYYYMMDDTHHMMSSZ`) used by apt, or `latest` for the live Debian mirrors. Only applies to Capsid's default images (`W019` with `base_image`). |
| `base_image` | string | — | Replaces the runtime image (and, for `uv-pypi` and source builds, the builder). Must be Debian-based and should be pinned by digest (`W017`). |
| `source_date_epoch` | integer | `1700000000` | `SOURCE_DATE_EPOCH` for the build; drives image and file timestamps. Rarely needs changing. |

Only the groups `build` and `run` are used (`W018`). Package names are Debian bookworm package names.

## `test`

Every recipe needs a test that exercises the packaged tool. It runs after `capsid build`, before any
push, and again on each architecture after publication.

```yaml
test:
  command: samtools view -c /test/sample.sam
  expected_output: "2"
  files:
    sample.sam: |
      @HD	VN:1.6	SO:unsorted
      r1	4	*	0	0	*	*	0	0	ACGT	IIII
      r2	4	*	0	0	*	*	0	0	TTGA	IIII
```

| Field | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `command` | string | — | **Required.** Run with `bash -c` as user `bio`. Must not be trivial (`true`, `exit 0`, `echo`, … are rejected by `E030`). |
| `expected_exit_code` | integer | `0` | Exit code the command must return. Useful for tools that print usage and exit `1`. |
| `expected_output` | string | — | Substring that must appear in the combined stdout and stderr. |
| `timeout` | integer | `60` | Seconds before the test is aborted and reported as failed. |
| `files` | map path → content | `{}` | Input files written to `/test` before the command runs. Paths are relative and may contain subdirectories; `..` is not allowed. |
| `output_file` | path | — | File the command must create, relative to `/test`. |
| `expected_checksum` | string | — | SHA-256 the `output_file` must have. Requires `output_file` (`E015`). |
| `random_seed` | integer | — | Exported as `CAPSID_RANDOM_SEED` and `PYTHONHASHSEED`, to make stochastic tools deterministic. |

When `files` or `output_file` is used, a temporary directory is mounted at `/test` and becomes the
working directory. Docker and Podman use `-v`/`-w`; Apptainer and Singularity use `--bind`/`--pwd`.

A checksum test pins the scientific result, not only the fact that the binary starts:

```yaml
test:
  command: seqkit seq --reverse --complement in.fa > out.fa
  files:
    in.fa: |
      >s1
      ACGTTT
  output_file: out.fa
  expected_checksum: <sha256 of the expected out.fa>
```

Compute the checksum once from a trusted run (`sha256sum out.fa`) and check that the content is
correct before committing it.

## Metadata: FAIR, RO-Crate and labels

Capsid writes this metadata into every image (see [Image design](image-design.md#embedded-metadata)):

- **OCI labels**: title, version, description, URL, license, vendor, source repository, DOI, EDAM
  terms, the Capsid version and build type, plus everything in `labels`.
- **SPDX 2.3 SBOM** at `/etc/capsid/sbom.spdx.json`, listing the tool and its locked packages.
- **RO-Crate 1.1** at `/etc/capsid/ro-crate-metadata.json`, describing the image as a
  `SoftwareApplication` with its license, DOI, EDAM terms and embedded files.

`ro_crate` adds JSON-LD to the RO-Crate. Top-level keys are merged into the root `Dataset`
(the keys `@id`, `@type` and `hasPart` are reserved). Entities under `@graph` are added to the
graph, replacing any existing entity with the same `@id`:

```yaml
ro_crate:
  author: {"@id": "https://orcid.org/0000-0002-1825-0097"}
  funder: {"@id": "https://ror.org/00x0x0x00"}
  "@graph":
    - "@id": https://orcid.org/0000-0002-1825-0097
      "@type": Person
      name: Josiah Carberry
```

## Lockfiles

`capsid lock <recipe.yaml | stack.yaml>` resolves the complete dependency closure inside the same
digest-pinned pixi or uv image that the build uses, and writes:

| Definition | Build type | Lockfile |
| :--- | :--- | :--- |
| `recipes/<name>/<version>/recipe.yaml` | `pixi-conda` | `pixi.lock` (one environment per platform in `platforms`) |
| `recipes/<name>/<version>/recipe.yaml` | `uv-pypi` | `requirements.lock` (with `--hash` lines) |
| `stacks/<name>.yaml` | — | `<name>.pixi.lock` and/or `<name>.requirements.lock` |

Source and binary recipes have no lockfile: the `sha256` fields pin their inputs.

The lockfile is embedded in the generated Dockerfile, so the Dockerfile is self-contained. Run
`capsid lock` again whenever you change `conda_packages`, `channels`, `package`, `python_version` or
`platforms`; the linter reports a lockfile that no longer matches the recipe (`E016`, `E017`).

## Stacks

A stack installs several `pixi-conda` and `uv-pypi` recipes into one image: all conda packages share
one environment and all PyPI packages share one virtual environment.

```yaml
# stacks/variant-calling-stack.yaml
name: variant-calling-stack
version: 1.0.0
description: Samtools and BCFtools for variant calling and VCF manipulation
components:
  - recipe: samtools
    version: '1.25'
  - recipe: bcftools
    version: '1.25'
test:
  command: samtools --version && bcftools --version
```

| Field | Type | Required | Description |
| :--- | :--- | :---: | :--- |
| `name` | string | yes | Stack name (same rules as a recipe name); the file must be `stacks/<name>.yaml`. |
| `version` | string | yes | Stack version, independent of the component versions. |
| `description` | string | | One-line summary. |
| `components` | list | yes | Recipes to include: `recipe` (name) and `version`. Without `version`, the highest available version is used (`W051`). |
| `test` | object | yes | Same fields as a recipe [`test`](#test); should exercise every component. |
| `apt_snapshot` | string | | Same as `build.apt_snapshot`. |

Rules checked by `capsid lint` and at build time:

- Components are found in `$CAPSID_RECIPES_PATH` (`:`-separated), `./recipes`, `./capsid-hub/recipes`
  and `../capsid-hub/recipes`, in that order (`E051`).
- Only `pixi-conda` and `uv-pypi` components are supported (`E052`).
- The image is built for the platforms that all components support; there must be at least one
  (`E053`).
- `uv-pypi` components must use the same `python_version` (`E055`).
- Because the conda packages share one environment, their versions must be compatible with each other
  (for example, samtools and bcftools built against the same htslib). `capsid lock` fails if they
  are not.

The stack's `labels` include `io.capsid.type=stack` and `io.capsid.components=<name>@<version>,...`.

## JSON Schema

`capsid schema` writes `recipe.schema.json` and `stack.schema.json` (JSON Schema 2020-12), generated
from the same data model the CLI uses. Capsid Hub publishes them under `schema/`.

To get validation and completion in editors that use the YAML language server (VS Code, Neovim,
JetBrains, …), add this first line to a recipe:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/LaBiOmicS/capsid-hub/main/schema/recipe.schema.json
```

The schema checks types, patterns and required fields. Rules that depend on several fields or on
other files (checksums for source builds, lockfile freshness, stack resolution) are enforced by
`capsid lint`.

## Writing a good recipe

- Start from `capsid init`, then review every field it filled in.
- Pin exactly: `samtools==1.25`, not `samtools` or `samtools>=1.20`.
- Run `capsid lock` and commit the lockfile.
- Use SPDX license identifiers.
- Keep `dependencies.run` minimal: everything there ends up in the image.
- Write a test that would fail if the tool were broken. Running `--version` is the minimum; a
  small input with an `expected_output` or `expected_checksum` is better.
- Run `capsid lint --strict` and `capsid build` before opening a pull request.
